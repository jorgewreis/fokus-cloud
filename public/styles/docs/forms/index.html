Documentação do sistema de formulários

Formulários que orientam.

Um formulário é uma conversa: pede uma informação, explica por que ela é necessária, confirma quando tudo está certo e ajuda a pessoa a corrigir o caminho quando algo dá errado. O Fokus Styles organiza essa conversa com semântica, estados previsíveis e mensagens que respeitam o contexto.

Este guia acompanha a construção de um cadastro completo de pessoa usuária, dos fundamentos da estrutura até o laboratório final. Os exemplos usam as classes oficiais do framework e mostram a relação entre HTML, aparência, interação e acessibilidade.

01 · Fundamentos

Preencher não deve ser adivinhar.

Antes de escolher um componente, deixe claro qual decisão está sendo solicitada. Um bom formulário reduz memória, apresenta o contexto no momento certo e permite revisar os dados antes de concluir.

Um campo por decisão.

Quando duas informações têm significados diferentes, elas devem poder ser lidas, preenchidas e corrigidas separadamente.

Use assim

Explique o que precisa ser informado, associe um label visível ao campo e ofereça ajuda antes que o erro aconteça.

Evite assim

Peça dados sem contexto, esconda instruções em placeholders ou faça a pessoa descobrir as regras apenas depois de falhar.

02 · Estrutura

O HTML conta a história do formulário.

Use `form` para a tarefa, `label` para nomear campos, `fieldset` e `legend` para agrupar decisões relacionadas. A estrutura semântica continua compreensível mesmo quando o CSS muda, a tela aumenta ou uma tecnologia assistiva assume a leitura.

Dados de contato
HTML · Estrutura semântica
<form>
    <fieldset class="fs-form-fieldset">
        <legend>Dados de contato</legend>
        <label class="fs-form-label" for="email">Email</label>
        <input class="fs-form-control" id="email" type="email" required />
    </fieldset>
</form>

Use assim

Faça a ordem do HTML acompanhar a ordem de preenchimento e use atributos nativos como `type`, `autocomplete` e `required`.

Evite assim

Construa o formulário apenas com divs, labels visuais soltos ou elementos que parecem campos, mas não funcionam como controles nativos.

03 · Campos

Cada informação tem seu controle.

Escolha o tipo de campo que corresponde ao dado e ao dispositivo. O navegador pode oferecer teclado, preenchimento automático e validações adequadas quando a semântica é correta.

Use assim

Escolha `email` para email, `number` para números e `select` quando as opções forem conhecidas. Dê ao controle um label permanente.

Evite assim

Use um input de texto para tudo, substitua labels por placeholders ou obrigue a pessoa a lembrar o formato esperado.

04 · Agrupamento

Grupos tornam decisões longas menores.

Quando vários controles respondem à mesma pergunta, o agrupamento deve ser percebido visualmente e anunciado semanticamente. `fieldset` e `legend` criam essa relação sem depender de bordas ou títulos decorativos.

Preferências de comunicação
Use assim

Use `legend` para explicar a pergunta comum e mantenha cada opção com seu próprio input e label.

Evite assim

Use apenas um título visual ou misture opções de assuntos diferentes dentro do mesmo grupo.

05 · Validação

O erro precisa dizer o próximo passo.

Validação não é uma punição no final do formulário. Ela deve explicar o problema em linguagem humana, apontar o campo afetado e preservar tudo que já foi preenchido corretamente.

06 · Estados

O campo também comunica pelo estado.

Normal, foco, preenchido, erro, sucesso, desabilitado e somente leitura são momentos diferentes. A cor ajuda, mas nunca deve ser a única forma de comunicar o estado.

Use assim

Combine mudança visual, texto e atributos apropriados. O foco deve ser evidente e o estado deve continuar compreensível em alto contraste.

Evite assim

Use apenas verde e vermelho para diferenciar sucesso e erro, ou retire o foco porque ele “deixa a tela feia”.

07 · Acessibilidade

Um formulário para pessoas reais.

Labels visíveis, foco, ordem de tabulação, mensagens associadas, contraste e alvos confortáveis formam o mínimo esperado. O formulário também deve funcionar com zoom, teclado, leitor de tela e diferentes formas de entrada.

  • Todo controle possui um label associado por `for` e `id`.
  • Campos obrigatórios usam `required` e uma indicação textual clara.
  • Mensagens de erro não dependem somente de cor ou posição.
  • Grupos relacionados usam `fieldset` e `legend`.
  • O foco permanece visível em todos os estados.
Regra de ouroSe a pessoa não consegue entender o que preencher, por que preencher e como corrigir, o formulário ainda não está pronto.
